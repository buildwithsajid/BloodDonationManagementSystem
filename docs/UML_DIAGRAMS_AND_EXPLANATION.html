Technical Explanation:

  • Entity Mappings: User maintains a 1:1 relationship with Donor. BloodGroup has a 1:N relationship with both Donor and BloodRequest.
  • Audit Trails: DonationHistory and DonorAvailabilityHistory link to Donor (the subject) and User (the updater), providing complete traceability.
  • Service & Controller Layers: Business logic is isolated inside @Service implementations (e.g., DonorServiceImpl) and exposed via @Controller classes returning strongly typed DTOs.

4.2 DFD Level 1 (Top-Level Functional Decomposition)

Decomposes the system into 4 core functional processes:

  • Process 1.0 (Authentication & User Management): Manages credential validation, BCrypt password verification, and session state against Data Store D1 (Users).
  • Process 2.0 (Donor Profile & Availability Engine): Handles donor enrollment, city indexing, and status toggles against Data Store D2 (Donors) and D6 (Availability History).
  • Process 3.0 (Blood Search & Requisition Engine): Filters available donors for emergency requisitions and logs hospital demands in Data Store D4 (Blood Requests).
  • Process 4.0 (Donation Recording & History Ledger): Commits verified clinical donation records to D5 (Donation History) and synchronizes last donation dates in D2 (Donors).

Technical Cardinality Summary:

  • users to donors: Exactly 1:1 (Enforced via Unique Foreign Key uq_donors_user_id).
  • blood_groups to donors: 1:N (Many donors share a single normalized blood group).
  • blood_groups to blood_requests: 1:N (Multiple hospital requisitions can demand the same blood group).
  • donors to donation_history: 1:N (A donor accumulates multiple clinical donation events over time).
  • donors to donor_availability_history: 1:N (An immutable audit trail of availability state changes).
